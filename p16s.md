## Protocol

`bench-p16.sh` — same 18k nonce-prefixed cold prompt as `bench-local.sh`, run as a **2×2 of
GPU DPM × CPU governor over 5 fully interleaved rounds** (all four arms visited each round,
20 runs, one server process throughout). Per-run GPU telemetry sampled at 1 Hz; medians over
samples with `gpu_busy_percent > 50`. Raw data: `p16s-bench-results.tsv`.

The 2×2 exists to close **TODO item 5**, which noted the 2026-08-07 run "moved DPM and
governor together, so the ~10% is not cleanly attributed to the governor alone."

## Result — steady state, rounds 2–5, n=4 per arm

| arm | PP | sd | TG | sclk | W | °C |
|---|---|---|---|---|---|---|
| dpm-auto / gov-powersave | 429.7 | 2.3 | 22.67 | 1971 | 24 | 71.5 |
| dpm-auto / gov-performance | 436.9 | 1.3 | 22.79 | 2012 | 24 | 66.2 |
| **dpm-high / gov-powersave** | **487.7** | 4.1 | 21.68 | 2899 | 55 | 91.5 |
| dpm-high / gov-performance | 481.4 | 1.0 | 21.45 | 2816 | 52 | 97.5 |

Main effects: **DPM `high` +12.6%**; **CPU governor +0.1%, i.e. nothing.**

## Three conclusions

**1. The P16s' untuned state nearly matches the p14's fully tuned state.**

| config | p14 | P16s |
|---|---|---|
| DPM `auto` (as-found) | 232 | **436** (+88%) |
| DPM `high` + bundled Mesa | 483 | **488** (+1%) |

The p14's *presenting problem* — a cold `auto` GPU pinned at ~1150 MHz / 13 W giving half
the documented prefill, which timed Qwen Code out mid-prompt — **does not occur here**. The
P16s' `auto` governor ramps to ~2000–2500 MHz / 24–32 W on its own. Tuned peak is the same
on both boxes (488 vs 483), which is the expected answer for identical silicon: the ceiling
is the SoC, and only the *floor* moved.

**2. The CPU governor is worth nothing, and TODO item 5 resolves the other way.**

Held at fixed DPM, `performance` is +1.7% at `auto` and **−1.3% at `high`** — it pulls the
GPU *down* (2816 vs 2899 MHz) and runs the package 6 °C hotter while doing it. On a shared
SoC power budget, a busier CPU is not free. The 2026-08-07 429 → 483 gain on p14 was DPM
and rep-order; the governor was along for the ride. **GNOME Power Mode → Performance is not
a throughput lever** — the half of it that mattered (DPM) is the half that switch doesn't set.

**3. DPM `high` is still the one real lever, but it is no longer free.**

On p14 it was +73% and obviously correct. Here it is +12.6% for **+31 W and +20 °C**. And
pair it with `powersave`, not `performance`: that combination is both faster (487.7 vs 481.4)
and 6 °C cooler. The `high`/`performance` arm reached **97.5 °C** and its clock sagged across
rounds (2892 → 2807 MHz) — it is the only arm that is thermally limited.

## Rep-order note — different mechanism, same rule

Round 1 of the `dpm-auto` arms reads 476.6, then settles to ~430 and stays. The `dpm-high`
arms show **no** round-1 effect. So this is chassis heat soak, not the GPU clock ramp the
README describes — but the operational rule is unchanged: **discard the first rep**, or use a
large n. Anyone benchmarking a cold laptop at DPM `auto` will measure ~10% too high.

## What to do on this machine

*(Written while the P16s was the machine in use. For the p14 as it stands today, see
`README.md` → "The 2026-08-22 re-measurement" — the advice there is different.)*

Nothing, for interactive use. 436 PP untuned is well clear of the timeout cliff that started
the p14 investigation. Run `sudo ~/p14/set-dpm-high.sh` before a long batch job if 12% is
worth 31 W and a 91 °C chassis; leave the CPU governor alone either way.
